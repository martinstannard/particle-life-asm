## What Martin asked for
"Add the different starting patterns that are in pl-box, and make it choose a new pattern every 20 seconds."

## What "the patterns" are
In `~/code/pl-box/crates/pl-core/src/rules.rs` the `RulePreset` enum lists 31 rule-matrix generators (Random, Symmetric, Snake, Chains1/2/3, RockPaperScissors, Bipartite, HubAndSpokes, ConcentricShells, AntiSymmetricSwirl, CheckerOffsets, DimersAndChains, TriadFlocks, SpiralConveyor, Patchwork, Wavefield, ChiralBandpass, RotatingConveyor, PrimeHop, ParityVortex, HelicalLadder, BiasedWave, ModularTriads, SkippedPursuit, BlueNoiseConveyor, OffsetPhasefield, RingRoad, TriSpiral, VortexAntivortex, DriftedPatchwork) with the display names from `RulePreset::name()`. Read that file in full (about 1,200 lines: how each generator builds `attraction`, `min_radius`, `max_radius` for K types) and also `preset.rs`, `simulation.rs` and `flow.rs` for how a preset is applied (force scale, friction, core repel, initial particle placement and colours). Port the generators faithfully so each produces the same kind of matrix as in pl-box.

## Requirements
1. **All 31 presets**, each producing the K x K attraction matrix (and per-pair min/max radius if pl-box varies them) for any K the program supports. Keep the existing simulation kernels untouched unless a preset needs a per-pair radius that the current layout cannot hold; if so, say what you changed and re-run the full test and the benchmark to show no speed regression (report before/after steps/s).
2. **Implementation language**: the preset selection, the matrix generation, the timer and the cycling are hand-written GNU `as` like the rest. If one or two generators are impractical in asm, a build-time generator (a small script in `tools/` that emits a `.S` data table) is an acceptable fallback for those only; say exactly which and why in the README. Do not move the runtime logic out of asm.
3. **Cycling**: every 20 seconds (default) choose a NEW preset and apply it: new rule matrix and a fresh scatter of the particles (a clear new start), same particle count and type count. Pick the next preset at random but never the one currently shown, and never repeat until all have been shown once (shuffle-bag). Make the interval an option: `--interval SECONDS` (0 disables cycling). Use a monotonic clock, not frame counting, so the interval is real time. Show the current preset name and seconds until the next switch in the window title (with FPS).
4. **Controls and options**: `--preset NAME` (case-insensitive, starts on that preset, and with `--interval` unset it still cycles; add `--no-cycle` to pin it), `--list-presets` prints the 31 names. Keys: Right/Left = next/previous preset in the list, C = toggle auto-cycle, R = re-roll the current preset (new seed, same preset), plus all existing keys. Update the `--keys` headless driver so tests can send these.
5. **Tests** (`make test`): (a) every preset yields a matrix of the right size with all attraction values in [-1,1] and radii sane (min < max, positive); (b) cycling logic: with a fake clock or a short `--interval`, headless run shows each preset exactly once before any repeats and never the same preset twice in a row; (c) for the deterministic presets (all except Random and any that use randomness), compare the asm matrix against pl-box's output for the same K. Get pl-box's reference values by running its own code if `cargo` works offline in `~/code/pl-box` (a tiny `cargo test`/example that PRINTS the matrices, run from a copy or with a separate target dir so pl-box is not modified); if it cannot run offline, derive reference matrices by hand-checking at least 5 presets against the Rust source and say that is what was done. Show the test output. Do not claim a preset matches without that evidence.
6. **Visual check**: add `--dump-frame` support with `--preset NAME` so a frame can be dumped per preset; produce a contact sheet (all 31 presets, small thumbnails, PNG) at `docs/presets.png` after a fixed number of steps so a human can see they differ. Convert PPM to PNG with `convert`/`magick` (installed). Look at it yourself and say honestly which presets look alike or look broken (e.g. everything collapses into one blob, or nothing moves).
7. **Speed evidence**: re-run `make bench` and report that the step speed is unchanged (1 and 8 threads, 10k/50k/200k). Note the cost of a switch (matrix build + re-scatter at 200k particles) in ms.
8. Update `README.md`: the preset list, new options and keys, how cycling works, what is generated at build time (if anything), the measured numbers and what is not done.
