# Port the asm Particle Life to AArch64 (NEON) for a Raspberry Pi 4 Model B

Same working rules as `TASK_particle_life_asm.md` (small conventional commits, NO AI attribution lines, no pushes, no secrets, only this repo, `free -g` before heavy steps, report to the conductor when done). Do not modify `~/code/pl-box`. Work on a NEW git branch `arm64` (create it from `main`); `main` and the x86-64 build must keep working and must not regress (`make test` on x86 must still pass on your branch).

## Goal
Martin wants this simulation on his Raspberry Pi 4 Model B (Cortex-A72, 4 cores, 1.5-1.8 GHz, NEON/ASIMD with FMA, NO SVE, NO dot-product extension, 64-byte cache lines, Raspberry Pi OS 64-bit based on Debian 13), driving a Waveshare 5.5" HDMI AMOLED, 1080x1920 portrait, through SDL2 (the same display that pl-box used). Today the core is x86-64 AVX2/AVX-512 assembly, which cannot run on ARM, so this is a port of the hand-written assembly to AArch64, not a recompile. The result should be as fast as practical on the A72 and keep the same features (presets, spawns, palettes, variable type counts, overlay, keys, options).

## What to port (read the existing code first)
`src/sim.S` (grid binning, force kernels), `src/threads.S`, `src/render.S` (software renderer + overlay font), `src/main.S` (options, SDL2 window, keys, bench, frame dump), `src/presets.S`/spawns/palettes (the preset/spawn/palette code you find under `src/`; list them with `ls src`). Keep `ref/` (C reference) and `tests/` shared with the x86 build so the SAME tests validate the ARM code.

## Design requirements
1. **Hand-written GNU `as` AArch64 assembly** (`.S` under `src/arm64/`), NEON 128-bit vectors (4 floats). Re-derive the kernels for 4 lanes; handle type counts up to 16 (K) with whatever lane grouping is fastest on NEON (say what you chose and why). Use `fmla`/`fmls` (fused), `ld1`/`st1` with post-index, `prfm` prefetch into the grid cells, structure-of-arrays like the x86 version. Target the in-order-ish dual-issue reality of A72: keep dependency chains short, interleave independent loads/FMAs, avoid long-latency ops in the inner loop. Measure alternatives on real hardware if available; otherwise reason from the ARM Cortex-A72 Software Optimization Guide and say it is unmeasured.
2. **Memory ordering**: the x86 code relies on x86 TSO (e.g. the spin barrier in `threads.S`). ARM is weakly ordered. Every cross-thread handoff and barrier must use the right acquire/release semantics (`ldar`/`stlr`, `ldaxr`/`stlxr` or LSE atomics `ldadd` only if the A72 has them: it does NOT, it is ARMv8.0, so no LSE) and `dmb ish` where needed. Treat this as the most likely source of silent bugs; add a stress test (many steps, 4 threads, compare against the single-thread result bit for bit).
3. **Threads**: default to 4 worker threads (the Pi has 4 cores); keep `--threads N`. Pin or not, justify.
4. **Display**: SDL2 on the Pi. Support the portrait panel: `--width 1080 --height 1920` and `--rotate 0|90|180|270` (rotate the finished pixel buffer in the renderer or when presenting, whichever is cheaper; say what you chose). Avoid per-frame full-screen conversions that would eat the frame budget: report the cost of presenting 1080x1920 (about 8 MB per frame) and the best SDL path (streaming texture upload vs software surface). Default window mode on the Pi should be fullscreen when `--fullscreen` is passed.
5. **Build**: a `Makefile` target for the ARM build (`make ARCH=aarch64`, outputs to `build-arm64/`). It must work in these ways, in this order of availability:
   a. Syntax check on this x86 desktop with `clang --target=aarch64-linux-gnu -c` (clang 22 is installed and can assemble AArch64, `ld.lld` too). Do this from the start, for every file.
   b. Logic tests on this desktop under emulation: needs `aarch64-linux-gnu-gcc`, `aarch64-linux-gnu-glibc` and `qemu-user` (Martin is being asked to install them with `sudo pacman -S aarch64-linux-gnu-gcc aarch64-linux-gnu-glibc qemu-user`; you cannot install packages yourself, no sudo). First check whether they exist (`which aarch64-linux-gnu-gcc qemu-aarch64`). If they do, build the headless test binary statically (`-static`) and run `make test ARCH=aarch64` under `qemu-aarch64`. If they do not exist yet, write everything, keep it syntax-clean with clang, and say clearly that logic is UNTESTED until the toolchain is installed; do not claim it works.
   c. Native build and test on the Pi itself: `make ARCH=aarch64` run on the Pi (Raspberry Pi OS has `as`/`gcc` after `sudo apt install build-essential libsdl2-dev`). Write `docs/PI.md` with exact steps (copy the repo with rsync/scp, build on the Pi, run `make test` and `make bench` there, run the window). The Pi's login is not set up yet (Martin may have to reset it), so you cannot reach it: do NOT try to log in or guess passwords. Prepare everything so it is one command once access exists.
6. **Tests**: `make test ARCH=aarch64` must run the same suites as x86 (core vs C reference and brute force, spawns, presets, overlay, cycling, switch/stale-rule detection, type counts 2..16) plus the 4-thread vs 1-thread bit-identical stress test. Show real output. Under qemu results are correct but speed means nothing: never quote qemu timings as performance.
7. **Speed evidence**: only real hardware numbers count. If you cannot run on the Pi, give your reasoning-based estimate clearly labelled as an estimate, and make `make bench ARCH=aarch64` ready to run on the Pi with the same output format as x86 so the numbers can be compared (10k/50k/200k particles at 1 and 4 threads, plus a pass at the panel resolution 1080x1920). Include a build-time-selectable fallback or compile flag if a kernel variant could be slower on A72, and tell Martin how to compare.
8. **README**: add an ARM64 section: design differences from x86 (lane width, barriers, prefetch), what was verified and how (clang syntax / qemu / hardware), exact commands, what is still unverified, and the realistic particle count expectation for a Pi 4 at 30 fps (label as an estimate unless measured).
